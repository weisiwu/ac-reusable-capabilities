# 目录与收录规则

## 仓库布局

```text
ac-reusable-capabilities/
├── catalog.json                  # 包和能力的机器可读入口
├── README.md                     # 读者总入口
├── CONTRIBUTING.md               # 贡献、契约和 PR 要求
├── demo/                         # 运行清单和启动器，调用包内真实示例
├── site/                         # Pages 站点与构建器，消费真实能力和 demo 清单
├── wiki/                         # 历史路径迁移存根，不维护并列正文
├── docs/                         # 统一文档中心：上手、能力地图、组合场景及维护说明
├── scripts/check_catalog.py      # 索引、路径及公开接口标记校验
├── packages/
│   └── python/
│       └── desktop/              # 能力领域，不是来源项目
│           ├── pyproject.toml    # 独立版本、依赖与构建
│           ├── LICENSE
│           ├── README.md
│           ├── src/ctf_desktop/   # 领域内部按职责划分模块
│           ├── tests/
│           ├── examples/
│           └── docs/             # 能力目录、契约、验证和来源
└── .github/workflows/            # 按受影响包执行验证
```

包路径统一为 `packages/<language>/<domain>`，目录使用小写英文和连字符。其他语言或领域仅在有可交付代码时创建，例如未来的 `packages/typescript/frontend`；不预建空包，不为每个来源项目建立一套目录。

## 包与能力的粒度

包是可独立安装、测试和版本化的交付单元；能力是包中可检索的职责单元。一个 Python 桌面包可以包含表格、查询和导航，不要求为每个辅助函数建立发行包。与桌面无关、已有独立使用者且版本周期不同的工程工具可另立领域包，不因为同为 Python 就塞进 desktop。

现有 `desktop` 保留 `ctf_desktop` 导入路径和发行名，避免迁入时强迫调用方改 import。迁入前安装的旧来源与本仓库版本是同一发行包的不同来源，不能同时安装；依赖切换由调用方显式执行。

## 新能力收录流程

1. 在 `catalog.json`、现有包的 README、公开接口标记和测试中检索关键词、行为及稳定标识。
2. 已有实现满足需求时直接复用；可兼容扩展时修改现有能力，补足新场景测试；行为冲突时记录差异和取舍，不按来源项目复制实现。
3. 确实需要独立领域包时，明确使用场景、边界、接口、依赖、许可和版本策略，再建立目录及索引。通用词如 `utils`、`common`、`misc` 不能作为不分职责的收纳区。
4. 每个包包含安装声明、README、源码、测试、可执行示例、公开契约、验证记录及来源许可说明；运行产物、私有环境、账号和业务数据不进入仓库。
5. 同步 `catalog.json`，运行索引校验及受影响包测试，通过 PR 审阅交付。未合并、未发布及未做目标设备验收分别记录，不混为完成。

## 标识和来源

- 包 ID 使用 `<language>.<domain>`，如 `python.desktop`；能力 ID 使用稳定语义名，如 `desktop.storage`。接口 ID 为 `desktop.storage.SqliteStore.backup`，迁移文件位置不改变已有身份。
- 机器索引列出包路径、能力 ID、模块、文档、测试和示例。源码公开接口保留 CONTRIBUTING 规定的全部标记，二者以校验脚本交叉核对。
- 来源属于能力的证据属性，不决定目录。多来源贡献写入能力所在包的来源文档；后续较复杂时可在包内 `docs/provenance/` 按迁入记录拆分，不放源项目代码副本。
- 公开仓库只写可公开的来源和许可事实；私有仓库地址、需求原文和个人知识库路径留在内部记录。第三方代码先核许可，不能以原创授权覆盖第三方许可。

## 版本和兼容性

每个包独立版本化，仓库不强行共用一个版本号。兼容扩展、新依赖和破坏性变更记录在包文档与 PR 中，已被使用的接口不得因来源项目更名而改名。跨包依赖必须显式声明，不能利用测试路径或源码目录注入形成隐含依赖。

本次只建立 Python desktop 包，其 `storage` 明确为明文 SQLite；未引入业务库迁移、密钥或代码保护配置。未来收录数据库加密、源码保护等能力时另立实际契约，禁止用同名模块推定已经支持。

## 文档与可执行示例

每个新增模块同时提供场景指南和公开契约；将最小例子纳入自动执行。Qt 专属契约使用 required_extra: qt 标记，例子检查器依据元数据跳过，不在工具中硬编码模块名。仓库级 `python scripts/check_docs.py` 校验本地 Markdown 链接，`python -O scripts/check_catalog.py` 确认生产校验不依赖可关闭断言。

根入口见 [文档中心](README.md)。每个新包同时登记 [demo 清单](../demo/catalog.json)，同步文档中心的[能力地图](能力地图.md) 及受影响 CI 路径；运行方式与资源退出要求见 [收录流程](能力收录流程.md)。

网站不以当前 desktop 示例决定能力类型。多来源关系、跨语言源码、演示方式与原生验证的分层契约见 [多类型能力与站点接入](多类型能力与站点接入.md)。
